# 로봇 모델과 동작 시나리오

6안 도면 로봇(`sp_description`)의 구조, 동작 스크립트(`maneuver.py`, `patrol.py`), 그리고 그 과정에서 찾은 문제와 해결 기록.
실행 명령은 [HANDOVER — 실행](HANDOVER.md#실행--터미널-4개) 참조.

## 동작 시나리오 — `maneuver.py`

주행 → 정지 → 몸체부 회전 → 전후단부 착지 → 구획 왕복을 **한 명령**으로 돌린다.
실행 방법은 [HANDOVER — 실행](HANDOVER.md#실행--터미널-4개) 참조 (Gazebo 는 따로 띄워 둔다).
전체 옵션은 `ros2 run sp_gazebo maneuver.py --help`.

순서:

| 단계 | 하는 일 |
| --- | --- |
| 0 | 론지를 따라 `-d` 만큼 주행하고 선다 (`/cmd_vel`, `/odom` 폐루프). **부호가 방향** — 기본 `-0.5` 는 −X 쪽 |
| 1 | 전후단부를 **0.64** 로 들어 **론지와 거더를 넘긴다** (0.50 이면 거더에 걸린다) |
| 2 | 몸체부를 90° 돌린다 — 전후단부도 같이 돌아 **론지와 수직**이 된다 |
| 3 | **전후단부만** −90° 되돌려 **다시 론지와 평행**하게 |
| 4 | 전후단부를 **0(통로 바닥)** 으로 내린다 — 처음과 같은 방향으로 착지 |
| 5 | **앞쪽(+X) 횡프레임 앞까지** 주행 |
| 6 | **뒤쪽(−X) 횡프레임 앞까지** 쭉 주행하고 선다 |

5–6 은 `--no-sweep` 으로 끌 수 있다.

**왜 회전한 뒤에야 구획 끝까지 갈 수 있는가.** 회전 전에는 전후단부가 X 로
±1.690 에 있어 로봇이 4.43 m 를 차지한다 — 5.91 m 구획 안에서 앞뒤로 0.74 m 뿐이다.
90° 돌리면 전후단부가 **X 가 아니라 Y 로** 벌어지고, X 에 남는 건 회전하지 않는
바퀴부(±0.826, 구동륜 바깥날 0.831)뿐이라 길이가 **4.43 → 1.66 m** 로 줄어든다.

    회전 전  ├──────────── 4.43 m ────────────┤   여유 1.48 m
    회전 후          ├─ 1.66 m ─┤                 여유 4.25 m
             ├────────────── 구획 5.91 m ──────────────┤

실측 (`ship_block_cad_world`, 스폰 x=−1.97): 참값 x **+0.061 ~ −3.998**, 총 6.6 m 주행.
그동안 z 는 0.5200 로, yaw 는 0.00° 로 **고정** — 바퀴부가 론지에서 안 벗어났고
프레임도 안 건드렸다. 프레임까지 남은 여유는 앞 84 mm / 뒤 87 mm.

정지 위치는 **오도메트리 기준**(`--spawn-x` + `/odom.x`)이라 `--margin`(기본 0.10 m)이
곧 오도메트리 오차 예산이다. 위 실측의 목표 대비 초과분 13~16 mm 는 제어 주기
0.05 s × 0.20 m/s 와 허용오차 0.01 m 이다. slip 이 크면 로봇은 자기가 선 줄 알고
프레임을 민다 — 여유를 늘리거나 `--sweep-speed` 를 낮출 것.

`--home`(복귀)은 **먼저 회전할 수 있는 자리로 돌아온다**. 되돌릴 때도 전후단부가
반경 2.229 m 를 쓰기 때문에 구획 끝에서는 몸체부를 되돌릴 수 없다. 회전했던 x 를
기억해 두고, 모르면 구획 중심(−1.97)으로 간다.

시작 자세(전 관절 0)는 몸체부가 바퀴부와 나란하고(= 론지와 평행), 전후단부도
론지와 평행하게 통로 바닥에 앉은 상태다.

전후단부는 몸체부의 **자식**이라 `/front_turn` `/rear_turn` 은 몸체부에 대한
**상대각**이다. 2)에서 가만두면 몸체부를 따라 수직이 되고, 3)에서 −90° 를 주면
월드 기준으로 처음 방향(론지와 평행)으로 돌아온다.

⚠ **회전할 자리를 남겨야 한다.** 제약이 둘인데 회전 쪽이 더 빡빡하다.

구획 중심은 횡프레임 안쪽 면 −4.925 와 +0.985 의 가운데, 즉 **x = −1.970** 이다.

| | 한계 | 허용 x 범위 |
| --- | --- | --- |
| 직진만 | 로봇 **4.425 m** 가 구획 5.91 m 안에 → 중심 ±0.743 m | −2.713 ~ −1.228 |
| 회전까지 | 전후단부가 **반경 2.229 m** 를 쓴다 → 중심 ±0.726 m | −2.696 ~ −1.244 |

반경은 회전축 1.690 + 끝단부 바깥 반길이 0.5225 (폭 0.2715 포함) 이다.
0.73 m 를 넘겨 놓고 돌리면 전후단부가 횡프레임을 때려서 회전이 안 끝나고 로봇이
밀려난다 (실측: 0.8 m 에서 발생).

**실측** — 스폰 −2.68 에서 앞으로 쭉 가면 **1.453 m** 뒤 x −1.2278 에서 전단
(x+2.2125 = +0.9847)이 앞쪽 횡프레임에 닿아 멈춘다. 뒤로 쭉 가면 −2.697 에서
후단이 뒤쪽 횡프레임에 닿는다.

⚠ **스폰 −2.68 은 회전 한계(−2.696)에서 16 mm 밖에 안 남는다.** 그 자리에서 바로
돌리지 말고 `-d 0.5` 로 앞으로 나온 뒤(−2.18, 여유 516 mm) 돌릴 것.

⚠ **전후단부 회전축 간격이 론지 pitch 의 정수배여야 착지가 통로 안에 들어온다.**
90° 돌리면 전후단부는 몸체부 중심에서 그 거리만큼 **론지를 가로지르는 방향**으로
떨어진 곳에 오는데, 통로는 pitch(0.845) 간격으로만 있기 때문이다.
도면 실측 ±1.5275 m 는 2배(1.690)에서 163 mm 모자라, 전후단부(폭 543)가
통로(695)를 벗어나 론지에 걸터앉는다.

| `end_turn_x` | 착지 후 `/ground_truth` z | |
| --- | --- | --- |
| 1.5275 (도면 실측) | **0.9552** — 로봇이 435 mm 들림 | ✗ |
| 1.690 (= 2 × pitch) | **0.5200** — 바퀴부가 론지 위 유지 | ✓ |

그래서 `params.xacro` 기본값을 **1.690** 으로 뒀다 (대신 로봇 길이가
4.100 → 4.426 m). **설계 확인이 필요한 지점이다** — 자세한 선택지는 `params.xacro`
의 해당 절에 적어 뒀다. 도면값으로 되돌리려면 그 파일에서 한 줄만 바꾸면 된다.

완료 판정은 `/joint_states` 관절 엔코더와 `/odom` 으로 한다.
상하·회전축은 움직여도 바퀴가 안 구르므로 `/odom` 에 안 나타나고,
`/ground_truth` 는 평가 전용이라 제어 루프에 넣지 않는다.
고정 시간 대기로 두면 시뮬이 느릴 때 동작이 덜 끝난 채 다음 단계가 나간다.

### 전후단부를 돌릴 때 덱이 출렁인다 — **블록 거더에 걸리는 것이었다**

**결론부터.** 진동도, 지지 형상 문제도, 회전 반력 문제도 아니었다.
**전후단부 아랫부분의 접지 롤러가 블록 거더의 수평 보강대에 걸려서** 회전축이 멈칫하고,
그 반력이 1.69 m 팔로 덱을 비튼 것이다. 들어올리는 높이를 고쳐서 없앴다.

| | 덱 yaw 편차 (C5 / E2) |
| --- | --- |
| `CLEAR` 0.500 (예전) | **6.79° / 8.20°** |
| **`CLEAR` 0.640 (현재)** | **0.19° / 0.10°** |

#### 어떻게 찾았나 — 구간별로 재니 **위치 의존**이었다

한 바퀴 전 구간에서 참값 자세와 관절값을 같이 기록해 국면별로 갈랐다.
그랬더니 국면도 회전 방향도 아니고 **로봇의 y 위치**가 갈랐다:

| 국면 | 로봇 y | 전후단부 회전 | Δ덱 yaw |
| --- | --- | --- | --- |
| 1변 C5 | **−0.877** | −90° → 0 | **6.79°** |
| 1변 E2 | −0.009 | 0 → −90° | 0.18° |
| 2변 C5 | −0.009 | −90° → 0 | 0.19° |
| 2변 E2 | **−0.854** | 0 → −90° | **8.20°** |

파형도 충돌 그 자체였다. 두 전후단부가 **완전히 동기로** 돌다가 −47.5° 에서
갑자기 후단부만 뒤처지고, 그 순간부터 덱이 밀린다. 동시에 pitch 0.236°,
z 1.6 mm 가 같이 튄다 — 반력만으로는 z 가 안 움직인다.

    turn  −89.6 … −47.5   덱 편차 −0.21° 로 **평평** (순수 회전 반력)
    turn  −47.5           후단부만 뒤처지기 시작 ← 여기서 닿는다
    turn  −16.5           덱 편차 **−6.81°** 최대
    turn    0             덱이 서서히 돌아옴

#### 무엇에 걸렸나 — 론지가 아니라 **거더**다

충돌 메시를 직접 훑었다. 블록 바닥에서 가장 높은 것은 론지가 아니다:

| 부재 | 상면 z |
| --- | --- |
| 통로 바닥판 | 0.070 |
| 론지 플랜지 | 0.520 |
| **좌현 거더(y −3.060)의 수평 보강대** | **0.590** |
| **우현 거더(y +2.995)의 수평 보강대** | **0.660** |

예전 기록이 "론지 중심 목록에 −3.871~−2.145 와 2.080~3.845 가 비어 있다"고 적어 둔
그 자리가 바로 **거더**다. 거더는 큰 경감공이 뚫린 판이라 아래위로는 통하지만,
경감공 사이 **수평 보강대가 론지보다 70~140 mm 높다.**

전후단부 회전축 둘레에서, 스윕 반경 0.591 m(아랫부분 상자 모서리)와 0.509 m
(접지 롤러) 안에 들어오는 블록 표면을 높이별로 세어 보면 **둘 다 최고가 0.590 이고
그 위로는 1.4 m 까지 완전히 비어 있다** — 즉 넘기만 하면 걸릴 것이 없다:

    z 0.50~0.52  ########################################################
    z 0.52~0.54  ####################################
    z 0.54~0.60  #####################
    z 0.60~1.40  (비어 있음)

`CLEAR` 0.500 이면 최하단(접지 롤러) 하면이 **0.567** 이라 0.590 보다 **23 mm 낮다.**
이 값으로 접촉 시작 각도를 역산하면 **−48.3°**, 실측 이상 발생 각도가
**−47.5°** 다. 이걸로 확정했다.

⚠ **y = −0.8775 는 기본 스폰 위치다.** 그 자리에서 덱이 수직이면 후단부 회전축이
y −2.5675 에 오고, 스윕 원이 좌현 거더(−3.060)를 물어 버린다.
y = −0.0325 에서는 두 회전축이 −1.7225 / +1.6575 라 일반 통로여서 안 걸린다.

#### 고친 것

`params.xacro` 에서 들어올림 높이를 **거더 상면 기준**으로 다시 잡았다.

```
block_girder_top  0.660                      ← 블록 내부 최고 거더 보강대 상면
end_lift_clear    0.640  (= 0.660 − 0.070 + 0.05 여유)
end_lift_up       0.660  (관절 상한, 0.500 → 0.660)
```

`patrol.py` 의 `CLEAR` 와 `maneuver.py` 의 `--lift-clear` 기본값이 같은 0.640 이다.
필요 높이는 자리마다 다르고 0.640 이 전부를 덮는다:

| 회전 자리 | 스윕 원 안 최고 구조물 | 필요 `CLEAR` | 0.640 의 여유 |
| --- | --- | --- | --- |
| 좌현 거더 옆 — 후단부 (로봇 y −0.8775) | 0.590 | > 0.520 | **120 mm** |
| 우현 거더 옆 — 전단부 (로봇 y +0.8125) | 0.660 | > 0.590 | **50 mm** |
| 일반 통로 (로봇 y −0.0325) | 0.520 (론지) | > 0.450 | 190 mm |

(회전축 둘레 반경 0.591 m 안의 블록 표면을 삼각형 단위로 샘플링해 구한 값이다.
전후단부 아랫부분 하면 = 통로 바닥 0.070 + `CLEAR`.)

**한 바퀴 재측정** — 전후단부를 돌리는 네 구간이 전부 0.2° 아래로 내려갔고,
roll·pitch·z 가 정확히 0 이다 (= 아무 데도 안 닿는다).

⚠ **설계 확인 사항 — 도면 스트로크로는 이 동작이 안 된다.**
전후단부 상하 스트로크는 도면상 `end_drop` = **450 mm** 이고, 그 만행정이
"전부 한 평면" 자세, 즉 **전후단부 하면이 론지 상면과 같은 높이**다 — 여유가 0 이다.
게다가 도면 시저는 접힘 254 mm 라 기구적 상한이 0.696 − 0.254 = **442 mm** 로,
론지(520)조차 못 넘는다. 예전 값 0.500 은 론지는 넘지만 거더는 못 넘었다.
**거더까지 넘으려면 640 mm 가 필요하다 — 도면보다 190 mm 더 길다.**
`end_turn_x` 와 같은 성격의 확인 항목이다: 시저 단수·바 길이를 키우거나,
전후단부 회전을 **거더에서 떨어진 자리에서만** 하도록 운용을 제한해야 한다.
(운용 제한 쪽을 택하면, 회전축 간격 ±1.690 과 거더 위치 −3.060 / +2.995 로부터
회전 가능한 스폰 Y 는 **−0.0325 하나뿐**이다 — ㅁ자 순회는 성립하지 않는다.)

지금 모델에서는 만행정에서 X자 시저가 신장 **59 mm / θ 1.69°** 까지 납작해진다
(q=0 에서는 696 mm / 20.4°). 종동 링키지라 시뮬은 정상이지만, 실제 시저가 그만큼
접히지 못한다는 것이 곧 위의 확인 사항이다.

⚠ **횡주행 중 여유는 여전히 3 mm 다.** `C6` 이 전후단부를 론지 상면 높이
(`END_DROP` 0.450, 하면 0.520)로 내리는데, y −0.8775 에서는 후단부 끝 102 mm 가
좌현 거더 보강대(0.590) 위로 걸친다. 아랫부분 충돌 상자 하면이 0.593 이라
**3 mm** 로 지나간다. 실측으로는 두 바퀴 모두 안 닿았지만(Δz 0.1 mm) 여유가 없다.

#### 예전 진단이 왜 틀렸나 — "덱 방향"은 **거더와 완전히 교란돼 있었다**

예전에는 "덱이 론지와 수직일 때만 흔들린다(7.05° 대 0.80°)"고 정리했고,
그래서 **전후단부를 먼저 돌리고 덱을 나중에 돌리도록** 순서를 바꿨다.
그 조치는 **효과는 있었지만 이유가 틀렸다.**

· 덱이 **나란**하면 전후단부 회전축이 x ±1.690 에 있다 → 스윕 원이 y −1.47~−0.29,
  거더(−3.060)에서 멀다 → 안 걸린다.
· 덱이 **수직**이면 회전축이 y ±1.690 에 온다 → 후단부 스윕 원이 거더를 문다 → 걸린다.

즉 "덱 방향"이라는 변수는 "전후단부가 거더 옆에 있느냐"와 100% 같이 움직였다.
순서를 바꾼 것은 **회전을 거더에서 먼 자리로 옮긴 것**이라 먹혔다.
그 순서 자체는 지금도 유효하고 그대로 둔다 (A2 실측 0.112°).

그리고 **예전 시도가 전부 실패한 이유**도 이걸로 설명된다 — 속도·램프·게인·
반대 방향 회전은 전부 "반력을 줄이는" 손인데, 원인이 반력이 아니라 **접촉**이었다.
기록으로 남겨 둔다:

| 시도 | 덱 편차 | 바퀴부 yaw 편차 |
| --- | --- | --- |
| 그대로 (`body_turn_p` 2000) | 7.7° | 0.20° |
| 회전속도 4배 느리게 (0.41 → 0.10 rad/s) | 7.1° | 0.75° |
| 지령 추종형 램프 (lead 0.05 rad) | 7.8° | 0.16° |
| 한쪽을 딛고 한쪽씩 회전 | 6.8° | 0.99° |
| 두 전후단부를 서로 반대로 회전 | 6.1° | 0.67° |
| `body_turn_d` 10배 (25000) | 5.7° | 2.19° |
| `body_turn_p` 10배 (20000) | 3.0° | 5.01° |

⚠ **서로 반대로 돌려도 상쇄되지 않았던 것(6.1°)이 결정적 단서였다.** 순수한 회전
반력이라면 상쇄돼야 하는데 안 됐다 — 한쪽만 뭔가에 닿고 있었기 때문이다.

⚠ **관절 `<limit><velocity>` 는 gz 가 강제하지 않는다.** 0.15 rad/s 로 낮춰 두고
실제 각속도를 재니 0.41 rad/s 로 돌았다. 회전을 진짜로 늦추려면 **지령을 램프로**
올려야 한다. (이번 원인과는 무관하지만 사실이므로 남긴다.)

#### 계측 방법 — 다시 재려면

덱의 **세계좌표 yaw = 참값 바퀴부 yaw + `body_turn` 관절각**이다. 화면에서 보이는
값이 이것이고, 관절각만 보면 바퀴부가 같이 돌 때를 못 가른다.
`/ground_truth` 와 `/joint_states` 를 같이 받아 국면 로그(`/rosout` 의 patrol 단계)로
잘라 보면 위 표가 나온다. roll·pitch·z 를 반드시 같이 볼 것 — **접촉이면 반드시
그쪽이 같이 튄다.** 순수 반력이면 yaw 만 움직인다.


### 회전 반력으로 바퀴부가 돌아가지 않게 — 토크를 낮춘다

바퀴는 폭 150 mm 론지 플랜지 위에 **얹혀만** 있어서 마찰로만 버틴다. 횡방향·요를
잡아주는 게 없으므로, 몸체부(+팔 100 kg)를 90° 돌리면 그 반력이 바퀴부를 돌린다.

도면에 없는 부품(가이드 롤러 등)을 더할 수는 없으므로 **회전 토크를 낮춰** 푼다.
위치 제어기의 `cmd_max` 가 곧 최대 토크이고 그게 반력의 크기다.

| 회전 토크 | 회전 시간 | dyaw | dy |
| --- | --- | --- | --- |
| 8000 N·m | 7~8 s | **−0.830°** | −0.7 mm |
| **700 N·m** (현재) | 14~16 s | **−0.000°** | 0.0 mm |

⚠ **관절 마찰이 곧 정상편차가 된다** — `e = friction / turn_p`.
토크만 낮추고 마찰(50 N·m)을 그대로 뒀더니 목표 1.5708 앞 **1.546 에서 멈춰**
버렸다 (0.025 rad = 마찰/P, 계산과 일치). 마찰을 15 로 낮추고 I 게인을 올려
해결했다. 지금 관절 도달 오차는 0.39~0.50° 다.

조절은 `params.xacro` 의 `turn_p` / `turn_i` / `turn_d` / `turn_cmd_max` /
`turn_damping` / `turn_friction` 로 한다.

⚠ **이건 완화지 구조적 해결이 아니다.** 요 오차는 회전을 느리게 하는 만큼만 준다.
근본적으로는 바퀴부에 **횡방향 구속**(가이드 롤러 등)이 필요하다 — 실물에 그런
장치가 있는지 설계 확인이 필요한 지점이다. 시뮬로 얻은 정량 근거:
**구속이 없으면 90° 회전 한 번에 요가 0.83° 발생한다.**

**실측 (전 구간, `CLEAR` 0.640 적용 후)** — −0.5 m 지시에 `/odom` 0.520 m,
참값 x −1.970 → −2.491 (0.521 m). 1) 들기 0.640 · 2) 전후단부 −1.564 ·
3) 몸체부 +1.563 · 4) 착지 0.002.
전 구간 `/ground_truth` z = **0.5200 유지**, 바퀴부 yaw **0.000° 고정**
(바퀴부가 론지에서 안 뜨고 안 돌아간다). 국면별 덱 yaw 편차:

| 단계 | Δ덱 yaw | Δroll | Δpitch | Δz |
| --- | --- | --- | --- | --- |
| 1) 들기 0.640 | 0.000° | 0 | 0 | 0 |
| 2) 전후단부 −90° | **0.113°** | 0 | 0 | 0 |
| 3) 몸체부 +90° | 88.802° (지령분) | 0 | 0 | 0 |
| 4) 착지 | 0.627° | 0 | 0 | 0 |

`--home` 복귀도 정상 — 되돌린 뒤 전 관절 ≈0, z 0.5200.

## ㅁ자 순회 주행 — `patrol.py`

론지를 따라 종주행하고, 론지를 **가로질러** 횡주행해서 블록 내부를 ㅁ자로 돈다.

```bash
ros2 run sp_gazebo patrol.py                          # 한 바퀴 (종 1.2 m, 횡 1칸)
ros2 run sp_gazebo patrol.py --laps 2                 # 두 바퀴
ros2 run sp_gazebo patrol.py --length 0.4 --cross 1   # 짧게
ros2 run sp_gazebo patrol.py --dry-run                # 순서만 출력
```

### 이 로봇이 방향을 바꾸는 방법

바퀴부에는 조향도 회전축도 없다. 방향을 바꾸는 건 **전후단부를 딛고 몸체부
회전축을 쓰는 것**이고, 어느 쪽이 도는지는 **무엇이 땅에 닿아 있느냐**로 갈린다.

| 접지 상태 | `/body_turn` 이 돌리는 것 |
| --- | --- |
| 전후단부가 바닥을 딛음 | **덱** (덱에 매달린 전후단부도 같이 돈다) |
| 전후단부로 **잭업**해서 바퀴부를 띄움 | **바퀴부** (덱이 전후단부에 물려 고정) |

⚠ **잭업은 `end_lift` 를 음수로 주는 것**이다. q=0 이 통로 바닥이므로 더
밀어내리면 바닥이 막아서 로봇 전체가 들린다.
**실측: `end_lift −0.08` 에 로봇이 58 mm 뜨고, 그 상태의 `/body_turn +90°` 에
바퀴부가 세계좌표에서 −89.6° 돈다.**

### 한 바퀴 순서

    A 종주행 자세   전후단부를 옆 통로로 (덱 +90° → 전후단부 −90°) — 처음 한 번만
    B 종주행        론지를 따라 X 로
    C 코너          잭업(통로 바닥) → 바퀴부 +90° → 착지 → 전후단부도 90° → 전부 횡방향
    D 횡주행        론지를 가로질러 Y 로
    E 코너          전후단부 −90° → 통로 바닥에 내림 → 잭업 → 바퀴부 −90° → 복귀

⚠ **E 는 C 의 역순이 아니다.** 잭업을 론지 상면이 아니라 **통로 바닥**에서 하도록
순서를 바꿨다 — 통로 바닥은 어디에나 있어서 론지 배치를 안 탄다.

**횡주행은 바퀴가 론지 상면만 딛고 간다.** 측당 13개를 130 mm 피치로 촘촘히 깐 것이
여기서 값을 한다 — 론지 pitch 845, 플랜지 폭 150 이라 바퀴열(1.56 m)이 어느 위치에서든
플랜지 하나 이상을 물고 있다. 대신 통로를 지날 때마다 덜컹거린다.

**실측 한 바퀴** (ship_block_cad_world):

| | 종 0.4 m × 횡 1칸 | 종 1.2 m × 횡 1칸 (기본값) |
| --- | --- | --- |
| x 폐합 오차 | **6 mm** | **30 mm** |
| y 폐합 오차 | **5 mm** | **25 mm** |
| yaw 폐합 오차 | **0.35°** | **2.05°** |
| 소요 (벽시계) | 약 4분 | 약 9분 |

**`CLEAR` 를 0.640 으로 올려도 폐합 정확도는 그대로다** — 종 0.4 m × 횡 1칸을
고치기 전/후로 각각 돌렸는데 폐합 오차가 **x 9 mm · y 2 mm · yaw 0.34° 로 동일**했다.
덱 출렁임은 바퀴부를 건드리지 않고(Δ바퀴부 yaw 0.001°) 스스로 되돌아오는
과도현상이라 주행 오차에는 안 실린다. **화면에서 보기 싫고 기구에 무리가 갈 뿐이다.**
대신 들어올림 행정이 140 mm 늘어 상하 동작 하나가 4→16 초로 길어진다.

⚠ **한 바퀴에 벽시계로 5~10분 걸린다.** 실시간 계수가 0.15 안팎이라 1.2 m 주행 하나가
50초, 90° 회전 하나가 20~50초다. 죽은 게 아니니 진행률 로그(`… 0.6/1.2 m`)를 볼 것.

⚠ **마감시간은 고정이 아니라 "진전이 있으면 연장"** 이다. `--timeout` 은 기본 여유고,
실제 중단 기준은 `--stall`(기본 25초 동안 **전혀** 진전 없음)이다. 느린 것과 기구가
걸린 것을 가르기 위해서다 — 고정 60초였을 때는 1.2 m 주행이 52.8초라 아슬아슬하게
실패하곤 했다.

### ⚠ 횡주행 거리는 아무 값이나 쓸 수 없다

횡주행이 끝난 자리에서 **바퀴부와 전후단부가 동시에 제자리를 찾아야** 한다 —
바퀴부는 이웃한 두 론지의 중점에, 전후단부(±1.690 = pitch 2칸)는 통로에.

도면 월드는 **론지 간격이 균일하지 않다** (−3.871~−2.145 와 2.080~3.845 에 하나씩
빠져 있다). ⚠ **그 자리는 비어 있는 게 아니라 거더다** — 론지 대신 전高 격벽이
서 있고, 그 수평 보강대가 론지보다 70~140 mm 높다. 그 구간으로 전후단부가 가면
통로에 못 앉고, 들어올려 돌릴 때도 보강대에 걸린다
(→ [전후단부를 돌릴 때 덱이 출렁인다](#전후단부를-돌릴-때-덱이-출렁인다--블록-거더에-걸리는-것이었다)).

**실측 — 이 블록에서 2칸은 안 된다.** y −0.8775 에서 2칸(1.690 m)을 가면 도착지
(+0.8125 근처)에서 전단부가 론지 +2.080 **하나에만** 얹혀 외날 위에 선 꼴이 된다.

| 코너 순서 | 결과 |
| --- | --- |
| 론지 상면에서 잭업 | 바퀴부가 안 뜬다 — `body_turn` 지령 0 에 실제 **1.569** |
| 전후단부 먼저 되돌리기 | 전단부가 끼어 안 돈다 — `front_turn` 지령 −1.571 에 실제 **−0.008** |

둘 다 재현했다. 원인은 **블록 형상**이다 — 2.080~3.845 는 론지가 아니라 **거더**라
전후단부(회전축에서 ±1.690)가 그 구간에 들어가면 지지를 잃는다.
**1칸(0.845 m)은 전 구간 정상**이라 기본값이 1 이다. 2칸을 쓰려면 그 구간에 론지를
채운 월드가 필요하다.

## 전후단부 구조와 시저 리프트

### ⚠ 전후단부는 한 덩어리가 아니다

도면 서브어셈블리가 셋으로 갈라진다 (`step_to_robot.py` 실측, 로봇 z):

    ┌── 덱 하면 0.454 ──────────────────────────────┐
    │  윗부분 (회전부 Ø400 + 상부 프레임)  0.384~0.454 │ 길이 1.040
    │    ↑ 몸체부에 붙어 **회전만** 한다  /front_turn  │
    ├────────────────────────────────────────────────┤
    │  시저 (X자)                          접힘 0.254 │ 길이 1.002 ← 유닛에 꽉 참
    │    ↕ 아랫부분을 바닥까지 내린다     /front_lift  │
    ├────────────────────────────────────────────────┤
    │  아랫부분 (궤도) — 바닥에 닿는다     0.000~0.130 │ 길이 1.050
    └────────────────────────────────────────────────┘

**축 순서가 회전 → 승강이다.** 예전 모델은 승강 → 회전이라 윗부분까지 통째로
내려갔는데, 그건 실제 기구와 다르다. 회전축이 위에 있으므로 `/front_turn` 을
돌리면 시저와 아랫부분이 **같이** 돈다 — 이것이 맞다.
지령 인터페이스는 그대로다 (`/front_lift` 는 여전히 미터, 0 이 바닥).

⚠ 도면의 시저 형상은 **접힌 자세로 굳어 있어 메시에서 뺐다.** 그대로 두면
아랫부분을 내렸을 때 늘어나지 않고 허공에 남는다. 바퀴부 도면 체인을 뺀 것과
같은 이유이고, 같은 자리에 파라메트릭 X자 바를 세워 대체한다.

**메시는 STEP 에서 뽑아 저장소에 커밋해 뒀다.** 도면이 바뀌면 다시 돌리고 커밋한다:

```bash
python3 src/sp_gazebo/scripts/step_to_robot.py \
    "cad/모바일 로봇 ASSY.stp" -o src/sp_description --proxy
```

`front_upper` `front_lower` `rear_upper` `rear_lower` 네 개가 나온다
(예전 `front_unit` / `rear_unit` 을 대체한다). 분류 경계는
`step_to_robot.py` 의 `END_LOWER_TOP_CAD_Y` / `END_SCISSOR_TOP_CAD_Y` 다.

### 바퀴부 ↔ 몸체부도 회전부 + 시저다

전후단부와 같은 구성이다. **회전부(턴테이블 Ø480)가 바퀴부에 얹히고, 그 위 시저**가
몸체부를 들어올린다. 축 순서도 같다 — 회전 → 승강.

    ┌── 덱 (몸체부) ─────────────────────┐  0.454~0.486
    │      ↕ 시저 2단, 바 1.55 m          │  접힘 110, 최대 260
    ├── 회전 프레임 (빔) ─────────────────┤  0.314~0.344
    ├── 회전부 (턴테이블 Ø480) ───────────┤  0.254~0.314
    │      ↻ /body_turn                   │
    ├── 바퀴부 (base_link) ───────────────┤  0.029~0.454
    └── 구동륜 26개 ─────────────────────┘

**시저 바는 바퀴부 앞뒤 길이(1.652 m)에 맞춘 1.55 m** 다 — 전후단부가 유닛 1.05 m
에 바 1.0 m 인 것과 같은 방식이다. 폭이 전 행정 1.545~1.549 m 로 유지된다.
그래서 앞뒤 두 조가 아니라 **한 조**다 (1.55 m 짜리 둘은 서로 겹친다).

⚠ 시저 하단 핀이 x ±0.775 로 나가는데 턴테이블(반경 0.24)이 그걸 못 받는다.
그래서 턴테이블 위에 **회전 프레임**(빔, x ±0.80)을 얹고 거기에 핀을 박았다.
프레임은 턴테이블과 한 링크라 `/body_turn` 을 돌리면 시저·덱과 함께 돈다.

⚠ **이 두 기구는 도면(6안)에 없다.** 도면에서 회전부(Ø400)는 양 끝단부(x ±1.5275)
에만 있고, 바퀴부 상면(0.454)과 덱 하면(0.454)은 딱 붙어 있어 사이가 비어 있지 않다.
실제 기구에는 있다고 하여 파라메트릭으로 세웠다 — 도면이 갱신되면 치수를 실측으로
갈아끼울 것. 사이 공간이 0 이므로 회전부(60)와 접힌 시저(60)는 바퀴부 상면 아래로
**120 mm 매립**된다. q=0 에서는 안 보이고 들어올려야 드러난다.

### 두 곳의 시저

    전후단부 (2단, 바 1000 mm)         몸체부 (2단, 바 1550 mm, 1조)
      q=0    신장 696 mm  θ 20.4°        q=0     신장 110 mm  θ  2.0°
      q=0.5  신장 196 mm  θ  5.7°        q=0.15  신장 260 mm  θ  4.8°
      폭 0.937~0.995 m                    폭 1.545~1.549 m
      → 내릴수록 펴진다                   → 올릴수록 펴진다

⚠ 몸체부 쪽 X자는 **납작하다**(θ 2.0°~4.8°). 행정이 150 mm 뿐인데 바가 1.55 m 라
기구적으로 그렇다 — 바를 길게 할수록 같은 신장량을 더 얕은 각도로 내게 된다.
전후단부가 시원하게 접히는 건 행정이 500 mm 라서다. 더 크게 벌어지게 하려면
바를 줄이거나 `body_lift_range`(0.15)를 키워야 한다.

**전후단부 바는 유닛 앞뒤 길이(1.05 m)에 맞춘다.** 도면 시저도 1.002 m 로 꽉 차 있다.
긴 바 2단이면 전 행정에서 폭이 **0.94~1.00 m** 로 유지된다 — 짧은 바를 여러 단
쌓으면 펼칠 때 폭이 확 줄어 유닛 안에서 가늘어진다.

전후단부 쪽 부호가 반대인 이유: 이 시저는 **윗부분에 매달려 아랫부분을 내리는** 기구다.

### 왜 종동 링키지인가

**시저는 닫힌 루프라 URDF 로 직접 표현할 수 없다.** 그래서 이렇게 나눴다.

- **하중과 행정** — 지금까지대로 `prismatic` 관절(`/body_lift` `/front_lift` `/rear_lift`)이
  전부 담당한다. 지령 단위(m)도, 제어 게인도, 측정 인터페이스도 **하나도 안 바뀐다.**
- **X자 바** — 그 행정을 따라가는 종동체다. 충돌체가 없고 하중을 받지 않으며,
  `scissor_driver` 노드가 각도를 풀어 넣는다.

⚠ **`mimic` 관절로 묶는 방법은 쓸 수 없다.** dartsim 이 지원하지 않는다 —
gz 가 이렇게 말한다: *"the chosen physics engine does not support mimic constraints"*.
bullet-featherstone 은 지원하지만, 엔진을 바꾸면 접촉·마찰 모델이 달라져
**이 저장소의 존재 이유인 드리프트 측정이 통째로 무효**가 된다.

### X자 격자를 트리로 어떻게 펴는가

바 길이 L, 각도 θ 일 때 스택 높이는 `N·L·sinθ` 이므로 **θ = asin(ext / (N·L))** 로 역산한다.
바를 **끝핀·중간핀**으로 엮으면 부착점이 전부 부모의 고정 국소좌표(±L, ±L/2)가 되어
θ 에 의존하는 부착점이 하나도 없다 — 그래서 보조축 없이 트리로 닫힌다.
관절값도 **θ 와 2θ 두 가지뿐**이고 부호는 `<axis>` 가 흡수한다.
스택 전체가 고정핀 하나에 매달리고 반대쪽은 자유단이라, 실제 시저의
**"한쪽 핀 + 한쪽 롤러"** 가 그대로 재현된다.

**검증** (`ship_block_drift`, 헤드리스):

| 항목 | 결과 |
| --- | --- |
| 관절 추종 오차 (전 행정) | 전후단부 **0.09°** / 몸체부 **0.07°** |
| 시저 끝단 ↔ 상대 플랫폼 | **0.70 mm** 이내 |
| 순기구학 이론값 (제어 오차 제외) | **0.000 mm** |
| 윗부분 상면 ↔ 덱 하면 (승강과 무관) | **0.00 mm** |

⚠ **게인은 조립체마다 다르다.** 바 길이가 4배 차이나면 관절축 관성이 70배
(0.003 → 0.2 kg·m²) 차이난다.

- **d 를 관성에 비해 크게 잡으면 목표 앞에서 멎는다** — 몸체부 바(0.24 m)에
  d=60 을 걸었더니 최대 12도 못 미친 채 정지했다.
- **작게 잡으면 중력에 밀려 과열린다** — 전후단부 바(1.0 m)에 d=2 를 쓰니
  주 체인이 +6도 벌어졌다.

⚠ **바 길이를 바꾸면 게인도 같이 바꿔야 한다.** 몸체부 바를 0.5 → 1.55 m 로
키우고 게인을 그대로 뒀더니 추종 오차가 0.42° → 1.3° 로 커졌다. 관절축 관성이
0.03 → 0.48 로 늘기 때문이다 (p 800 → 16000, d 2 → 110).

⚠ **`<initial_position>` 을 반드시 q=0 자세 각도로 준다.** 0 으로 두면 기동 후
`scissor_driver` 의 첫 지령이 오기까지 몇 초 동안 바가 **자유낙하**한다.
1 m 짜리 전후단부 바는 그 사이에 목표를 한참 지나쳐 넘어가고, 그 뒤엔 제어기가
붙어도 되돌아오지 못한다 (실측: 목표 40.7° 인데 112° 에서 정지).
q=0 이 스폰 자세이므로 각도는 도면값에서 그대로 나온다 — `θ₀ = asin(ext(0)/(N·L))`.

⚠ `scissor_driver` 가 안 떠도 시뮬은 정상 동작한다 — X자가 접힌 채(θ=0) 있을 뿐이고
주행·오도메트리·ESKF 는 아무 영향을 받지 않는다.

### ⚠ 성능 — 구동륜 촘촘 배치의 대가

| 구성 | 실시간 계수 (RTF) |
| --- | --- |
| 구동륜 16, 시저 없음, 팔 = 덩어리 하나 | **0.35** |
| 구동륜 26, 시저 없음 | **0.22** |
| 구동륜 26 + 시저 16관절 | **0.30** |
| + 회전부 + 팔 6축 (현재) | **0.15 ~ 0.17** |

접촉점이 16 → 26 개로 는 것이 첫 번째 비용이고, 팔 6축(링크·제어기 6개씩)이
두 번째다. 팔 충돌체를 끄면 0.15 → 0.17 로 조금 회복된다 (`arm_collision`).

⚠ RTF 측정은 편차가 크다(같은 구성에서 0.15~0.19). **gz 인스턴스가 여러 개 떠
있으면 수치가 통째로 오염된다** — 측정 전에 `ps -eo comm | grep -c ruby` 로 1 인지
확인할 것. 이 표의 앞 세 줄은 그렇게 다시 잰 값이다.
드리프트 실험처럼 긴 주행을 여러 번 돌릴 때는 시간이 두 배로 든다.
급하면 `params.xacro` 에서 되돌릴 수 있다 — 기구학·오도메트리는 바뀌지 않는다:

- 바퀴: `drive_wheel_n` 8 / `drive_wheel_x0` 0.77 / `drive_wheel_dx` 0.22
- 시저: `body_sc_n` 과 `end_sc_n` 을 **0** 으로 두면 X자 바와 제어기가 통째로 사라진다
- 팔 충돌체: `arm_collision` 을 **false** 로
  (전후단부의 상·하 분리와 회전→승강 축 순서는 그대로 남는다 — 그건 기구 구조지
  시각화가 아니다)

## 매니퓰레이터 — FANUC CRX-20iA/L 6축

캐리지 위에 서서 레일(행정 ±1.75 m)을 따라 덱을 왕복한다.

    베이스 → J1(요) → 숄더 → J2(피치) → 상완 710
           → J3(피치) → 전완 540 → J4(롤) → J5(피치) → 손목 168 → J6(롤) → 플랜지

| 토픽 | 내용 |
| --- | --- |
| `/arm_j1` … `/arm_j6` | 각 축 위치 [rad]. `std_msgs/Float64` |
| `/rail_cmd` | 캐리지 위치 [m], 0 = 행정 중심 |

```bash
ros2 topic pub -1 /rail_cmd std_msgs/msg/Float64 "{data: -1.5}"   # 뒤쪽으로 이동
ros2 topic pub -1 /arm_j2   std_msgs/msg/Float64 "{data: 0.6}"    # 어깨 들기
```

⚠ **도면의 팔 덩어리는 쓰지 않는다.** 접힌 자세로 굳어 있어 관절이 없고,
`J2ARM_UNIT_LONG` 등은 바운딩박스가 4.6 × 2.2 × 3.1 m 라 링크가 아니라 작동영역
(또는 오배치)이다. 그래서 `step_to_robot.py` 가 `arm.stl` 을 더 이상 만들지 않고,
URDF 가 공개 제원으로 6축을 세운다.

⚠ **링크 길이는 도달거리(1418 mm)에서 역산한 근사다** — J2 부터 플랜지까지
710 + 540 + 168 = 1418. FANUC 공식 치수도면이 들어오면 `params.xacro` 의 세 값을
갈아끼울 것. 관절 한계는 CRX-20iA/L 공개 사양 그대로다.

⚠ **관절값 0 은 팔이 곧게 선 자세**(플랜지 z ≈ 2.38 m)라 주행에 못 쓴다.
J2 90° · J3 −169° 접은 자세가 기본이다 (실측 포락 z 0.906~1.052, x −0.034~+0.720
— 블록 내부 5.18 m 에 여유롭다).

### 기본은 **고정**이다 — `arm_fixed`

```bash
ros2 launch sp_gazebo sim.launch.py arm_fixed:=false   # 6축을 살린다
```

기본값 `arm_fixed:=true` 면 팔 6축이 **접은 자세로 굳는다.** 관절도 제어기도
`/arm_j1`..`/arm_j6` 토픽도 사라진다. 주행 드리프트 실험에는 팔이 캐리지 위
**질량으로만** 관여하므로 이쪽이 맞다 — 과도상태가 없고 모델이 가볍다.
`arm_fixed:=false` 로 켜면 6축이 살아나고 자세를 줄 수 있다.
**두 경우의 팔 자세는 완전히 같다** (실측 포락 z 0.906~1.052, x −0.034~+0.720 일치).

## 색

**로봇 전체가 밝은 회색 하나다.** 예전에는 부위별로 색을 나눴는데(강재 회색 /
궤도 검정 / FANUC 파랑), 형상 확인에는 한 색이 낫다 — 색 경계가 아니라 실제 형상
경계가 보인다. `crawler.urdf.xacro` 의 `light` 재질 한 줄에서 바꾼다.
